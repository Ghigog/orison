# Orison — Knowledge, Retrieval & NPC Architecture

> **Document scope**: This is a living design reference for Orison's data pipeline, knowledge graph, and NPC agent systems. It captures the full diagnostic, research findings, architectural philosophy, and implementation plan agreed upon in June 2026 — along with tickets for Phase 1 (immediate fixes) and Phase 2 (semantic retrieval architecture). Future agents should read this document before touching `VaultCompiler.gd`, `KnowledgeGraphManager.gd`, `PromptBuilder.gd`, `SystemPrompts.gd`, `GameLoopController.gd`, or `EmotionEngine.gd`.

---

## 1. Product Philosophy

Orison's core idea is this:

> A user has a Markdown archive of world-building notes — completely disorganised, a personal data lake. Orison ingests it, builds a knowledge structure an AI can navigate, and uses that to generate a living story with the user as the protagonist.

This philosophy has several architectural implications that must be preserved across all development:

### 1.1 Everything Must Be Ingested

The vault is a data lake. Its internal structure — heading formats, tag conventions, numbering schemes — is irrelevant and will vary wildly between users. No information should ever be silently discarded. If a file section cannot be parsed into a canonical field, its content must still be available to the system in some form.

### 1.2 Local and Private

All computation must run on-device. No content from the user's vault or gameplay is ever sent to an external API. The LLM and embedding models run locally via Ollama. The knowledge graph, vector store, and memory system are local files.

### 1.3 Context Windows Are Finite — Retrieval Must Be Hierarchical

You cannot fit a novel-length vault into a 4K–8K context window. The solution is not compression — it is hierarchical retrieval:
- **Level 2 (campaign)**: Big-picture summaries of major arcs, factions, and themes
- **Level 1 (region/arc)**: What is happening in this part of the world?
- **Level 0 (scene/character)**: What are the specific facts about this NPC right now?

Each level is generated by a separate LLM pass with a fresh context window. The existing onboarding narrative hooks (SYS008) already implement this for session start. The same pattern must be applied continuously during gameplay.

### 1.4 The Director/Actor Split (Left Brain / Right Brain)

Orison has two models playing distinct roles:

| Model | Role | Speed | Responsibility |
|---|---|---|---|
| **Director** (`gemma4:e4b`) | The knowledge brain | Slow | Retrieves context, builds narrative beats, manages world state, decides what happens |
| **Actor** (`llama3.2:3b`) | The voice | Fast | Executes character dialogue based on what the Director prepared |

The Director must eventually become **agentic** — able to actively query the knowledge graph when it needs information ("what is beyond the swamp?"), not just receive a pre-assembled context prompt. The Actor never retrieves anything. It only speaks.

### 1.5 Biography vs. Session Memory

These are two distinct and separate concepts:

- **Biography** (`biography` field on KG nodes): What the character did before the current adventure — extracted from the vault files during compilation. This is static (until recompiled).
- **Session memory**: What the character did *in your game* — managed by `MemoryManager.gd` (SYS037) in three tiers: short-term (last N turns), medium-term (session summaries), long-term (distilled character memories). This is dynamic and grows during play.

These must never be conflated in the knowledge graph or NPC prompt.

## 2. Root Cause Diagnosis (June 2026)

A full diagnostic audit was performed across `VaultCompiler.gd`, `KnowledgeGraphManager.gd`, `PromptBuilder.gd`, `SystemPrompts.gd`, `GameLoopController.gd`, `EmotionEngine.gd`, and `CharacterVisuals.gd`. The following bugs were confirmed with exact line numbers.

### Bug 1 — Section Parsing Silently Drops Most Character Data

**Symptom**: `[VaultCompiler] Warning: Unrecognized section "**1. History**" — skipping` appears for almost every character file.

**Root cause**: `_normalize_section_name()` (VaultCompiler L874–877) strips spaces, underscores, and hyphens but does **not** strip Markdown bold markers (`**`) or numeric prefixes (`1.`, `2.`). Any heading formatted as `**1. History**` normalises to `"**1.history**"`, which never matches the alias `"history"`. The section's entire content is discarded.

**Impact**: For most characters, `backstory`, `personality`, and `appearance` are all empty after compilation. The LLM is roleplaying characters with zero source data.

### Bug 2 — Extracted Fields Are Never Used in the NPC Prompt

**Symptom**: Even for characters whose sections *do* parse correctly, personality and backstory never appear in gameplay.

**Root cause**: The CHARACTER PROFILE block in `SystemPrompts.get_character_agent_prompt()` (L94–97) contains only **three lines**: Name, Biography, and Affinity score. `personality`, `backstory`, `appearance`, and `goals` are stored in `props` but are never passed to `SystemPrompts` and never injected into the prompt. Additionally, `personality` is not included in the compatibility dict in `_compiled_data["characters"]` at all.

**Impact**: Every NPC responds with generic behaviour regardless of their vault file content.

### Bug 3 — Gender Hallucination (King Yuna)

**Symptom**: The Actor model generates "her eyes", "her throne", "she regarded" for King Yuna.

**Root cause**: There is no `gender` or `pronouns` field anywhere in the pipeline — not extracted, not stored, not injected. The `llama3.2:3b` model associates the name "Yuna" with a feminine statistical prior and uses feminine pronouns. The CHARACTER PROFILE block gives it no correction.

### Bug 4 — Triple Physical Reaction Generation (3 LLM calls per turn)

**Symptom**: Log shows three sequential `[CharacterVisuals] Querying reaction description for King Yuna...` and three reaction results per player message.

**Root cause**: `generate_physical_reaction()` is called from `apply_emotion()`. `apply_emotion()` is triggered by three independent code paths per turn:
1. NPC stream completion → `process_response_tags()` → `character_visual_update_requested` signal
2. `trigger_emotion_reflection()` completing → `process_response_tags()` again
3. `select_character()` at GameLoopController L650 emitting `character_visual_update_requested` with old emotion

**Impact**: 3 sequential LOW-priority LLM calls queued after every player turn, blocking the queue.

### Bug 5 — Lore Context Truncated to 409 Tokens

**Symptom**: `[KnowledgeGraph] Lore context (3590 tokens) exceeds budget (409 tokens)`.

**Root cause**: `context_limit = 4096` in `PromptBuilder.build_prompt()` (L133). The lore budget is `context_limit * 0.10 = 409 tokens`. The actual prompt at runtime reaches ~10,826 characters (~2,706 tokens) — already over the 4,096-token limit before lore or player input. Ollama silently truncates the prompt on its side.

**Impact**: The NPC receives essentially no world lore. The Director can't do its job.

### Bug 6 — Emotion System Frozen (Same Values Every Turn)

**Symptom**: `[SYSTEM] King Yuna feels: Serenity (intensity: 0.6) | Rapport: -0.05` repeats identically across all turns.

**Root cause (compound)**:
1. The `llama3.2:3b` model returns boilerplate emotion JSON on every turn because the biography is empty (Bug 1 + Bug 2).
2. `trigger_emotion_reflection()` overwrites the turn's emotion with an identically boilerplate reflection result.
3. `decay_emotions()` skips the active character — so even if a delta arrives, it is overwritten.
4. The no-op delta (identical emotion + intensity) still emits `character_visual_update_requested`, queuing another reaction generation.

### Bug 7 — Director Fires Too Infrequently

**Symptom**: NPC sits passively for many turns, saying "Oh, a quest? Sure, go ahead."

**Root cause**: The Director triggers only when `turns_since_last_director >= 6` AND the `escalation_signal` is non-`"none"`. With a 3B model that almost never returns a non-`"none"` escalation, the Director only fires after 6 dead turns. When it does fire, its narrative beat is not injected into the NPC's subsequent prompt — so the NPC still doesn't know what the Director planned.

## 3. Research Findings — State of the Art (June 2026)

The following summarises research into the flagship approaches for knowledge retrieval, hierarchical context, and local AI. All approaches below are fully local (no external APIs).

### 3.1 GraphRAG (Microsoft, 2024)

**What it is**: Transforms a document corpus into a hierarchical knowledge graph with LLM-generated community summaries at multiple abstraction levels.

**How it works**:
1. Documents are chunked (~600 tokens each)
2. An LLM extracts entity/relationship triples from each chunk: `(Aldric) --[son_of]--> (Lord Varek)`
3. All triples are merged into a property graph
4. **Leiden algorithm** clusters the graph into communities at multiple resolution levels
5. An LLM generates a **Community Report** for each community at each level — a pre-written thematic summary
6. At query time: broad questions use high-level community reports; specific questions use entity-level graph traversal

**Local capability**: Yes — `pip install graphrag`, configure `settings.yaml` to point at Ollama. Indexing is LLM-call-heavy (expect 200–500 calls for a 50-file vault, 30–90 minutes on M-series Mac). Incremental updates are cheaper.

**Orison relevance**: VaultCompiler already does GraphRAG Phase 1 (entity extraction from Markdown into a KG). What's missing is community detection and hierarchical summary generation. GraphRAG community reports would populate the Director's campaign-level context slot much more intelligently.

**Practical path**: Run as a Python sidecar at vault compile time. Import community reports as `"summary"` nodes into `KnowledgeGraphManager`.

---

### 3.2 RAPTOR — Recursive Abstractive Processing (Stanford, ICLR 2024)

**What it is**: Builds a tree of progressively broader LLM-generated summaries from document chunks. Leaves = raw text. Each level up = a summary of a cluster of the level below. Retrieval can target any level.

**How it works**:
1. Embed all raw text chunks (leaf nodes) with a local model
2. UMAP reduces 768D embeddings to ~5D for clustering
3. Gaussian Mixture Model (GMM) soft-clusters leaves — a chunk can belong to multiple clusters
4. LLM summarises each cluster → Level 1 nodes
5. Repeat until a single root summary remains
6. At query time: retrieve across all levels (collapsed retrieval) or traverse the tree top-down

**Orison relevance**: This is the exact "big picture → region → scene → character" zoom architecture described in the product philosophy. RAPTOR levels map directly:

| RAPTOR Level | Orison Equivalent |
|---|---|
| Root | Campaign overview — what is this story about? |
| Level 2 | Arc/region summaries — "the Northern political arc" |
| Level 1 | Scene/chapter — specific events, session history |
| Leaf | Raw vault notes — character biography paragraph |

`MemoryManager.gd` already manually implements a 3-tier memory hierarchy during play. RAPTOR would add an *offline-compiled* version over vault files — so the Director has campaign-level awareness from session 1.

**Local capability**: Yes — adaptable with Ollama for LLM calls and `nomic-embed-text` for embeddings. Official repo at `github.com/parthsarthi03/raptor`.

---

### 3.3 Agentic RAG (ReAct Pattern)

**What it is**: The LLM actively decides what to retrieve during its reasoning, rather than receiving a pre-assembled context. It uses a Reason → Act → Observe loop.

**How it works**:
```
Thought: The player is leaving the swamp. I need to know what's beyond it.
Action: search_knowledge_graph("swamp exit connections Jiggerook")
Observation: The Jiggerook swamp borders the Ashfield plains to the north...
Thought: I also need to know if there's any conflict in the Ashfield.
Action: search_knowledge_graph("Ashfield conflict factions")
Observation: The Ashfield Accord was broken in Year 3 of the Silence...
Thought: Sufficient context. Generating narrative beat.
Final: [narrative beat]
```

**Orison relevance**: Orison's Director already generates narrative beats. The upgrade is giving it **tool access** to the knowledge graph mid-generation. This is the true realisation of "left brain / right brain" — the Director actively researches before speaking.

**Local capability**: Yes — implementable in pure GDScript using `LLMClient.gd`'s existing JSON mode. No framework required.

---

### 3.4 Local Semantic Embeddings

The current `retrieve_context()` uses substring matching on node labels. This means "the blacksmith's apprentice" will never find a node labeled "Aldric". Semantic embeddings fix this.

**Recommended stack**:

| Component | Choice | Reason |
|---|---|---|
| Embedding model | `nomic-embed-text` via Ollama | 137M params, fast, 768-dim, tested |
| Vector storage | `sqlite-vec` GDExtension | Same SQLite file as save game, GDScript-compatible |
| Retrieval | Hybrid BM25 + KNN via RRF | 15–25% accuracy improvement over either alone |

**Reciprocal Rank Fusion (RRF)** merges keyword and semantic rankings without score normalisation:
```
score(doc) = Σ 1 / (60 + rank_i(doc))
```

**Embedding call**: POST to `http://localhost:11434/api/embeddings` — identical to existing LLM calls in `LLMClient.gd`.

---

### 3.5 Narrative AI Research Findings (2025–2026)

- **Director/Actor split is the 2025 consensus** for AI-driven narrative games. Orison already implements this correctly.
- **Knowledge Graphs outperform vector DBs for causality** in narrative contexts — KGs encode *why* events happened, not just *what*. Orison's use of a KG is the right architectural choice.
- **Context drift** is the #1 failure mode in long campaigns. Mitigated by structured state injection (Orison's `CampaignState`) and periodic consistency checks.
- **AI Dungeon's architecture** uses tiered context ("story cards" retrieved by keyword) — essentially BM25 retrieval. Orison's current architecture is more sophisticated.
- **Graphiti** (open source, 2025): Temporal knowledge graphs for agent memory — tracks *when* facts were learned. Relevant for future session-to-session memory continuity.
- **Constrained generation wins**: The most successful narrative AI systems use the LLM to fill in micro-narrative details between hand-authored beats, not for fully autonomous generation. Orison's system prompt engineering (SYS002, SYS027) already enforces this correctly.

## 4. Implementation Plan

### Phase 1 — Immediate Fixes (Gameplay Blockers)

These fix the bugs preventing basic gameplay from working. No new dependencies required.

#### 4.1 Replace Section Parsing with LLM Extraction (Fixes Bugs 1, 2, 3)

**File**: `VaultCompiler.gd`

Replace `_extract_character_sections()` and `_normalize_section_name()` and `_init_section_aliases()` entirely. Instead, after reading the raw markdown body, make a single JSON-mode LLM call to the Director model:

```
Prompt: "Extract the following fields from these character notes as JSON:
{
  biography: "Their history and past adventures",
  personality: "Their traits and temperament",
  appearance: "Their physical description",
  gender: "Their gender and pronouns (e.g. 'male, he/him')",
  goals: "Their motivations and current goals"
}
Notes: [raw markdown]"
```

Store the extracted fields in node `properties`. Remove ALL `[VaultCompiler] Warning: Unrecognized section` log lines.

Update the `_compiled_data["characters"]` compatibility dict to include `personality`, `gender`, `goals`.

#### 4.2 Wire All Fields into the NPC Prompt (Fixes Bug 2)

**Files**: `PromptBuilder.gd`, `SystemPrompts.gd`

Pass `personality`, `appearance`, `gender`, `goals` from the character dict through `PromptBuilder.get_character_agent_prompt_for_id()` into `SystemPrompts.get_character_agent_prompt()`.

Expand the CHARACTER PROFILE block:
```
CHARACTER PROFILE:
- Name: {name}
- Gender/Pronouns: {gender | "Infer from title and biography. Never assume from name alone."}
- Biography: {biography}
- Personality: {personality}
- Appearance: {appearance}
- Goals & Motivations: {goals}
- Relationship with Player: {label} ({affinity})
```

Raise `context_limit` from `4096` to `8192`. Raise lore budget from `0.10` to `0.15`.

#### 4.3 Debounce Physical Reaction Generation (Fixes Bug 4)

**File**: `CharacterVisuals.gd`

Add `var _reaction_pending: bool = false`. Guard `generate_physical_reaction()` with `if _reaction_pending: return`. Reset in LLM callback (both success and error). Remove call from `apply_emotion()`. Move single authoritative call to `GameLoopController._on_npc_stream_completed()`.

#### 4.4 Lower Director Threshold + Inject Narrative Beat (Fixes Bug 7)

**File**: `GameLoopController.gd`

Change `turns_since_last_director >= 6` → `turns_since_last_director >= 2`. After `consume_pending_scene()`, store Director narration in `CampaignState.last_director_beat`. Inject into NPC context in `PromptBuilder.build_prompt()` as `"[Narrative Context]: {beat}"`.

#### 4.5 Emotion No-Op Delta (Fixes Bug 6 partially)

**File**: `EmotionEngine.gd`

Before emitting `character_visual_update_requested`, compare new emotion + intensity against current stored values. Skip emit if identical. Log `[EmotionEngine] No delta — skipping visual update`.

### Phase 2 — Architectural Upgrades (Retrieval Quality)

These implement the correct long-term retrieval architecture. Not required for Phase 1 but represent the path forward.

#### 4.6 Semantic Embeddings + sqlite-vec

1. Add `LLMClient.get_embedding(text: String) -> Array[float]` — POST to `/api/embeddings` using `nomic-embed-text`
2. Add `EmbeddingStore.gd` autoload — wraps `sqlite-vec` GDExtension for BLOB storage + KNN SQL queries
3. At `VaultCompiler` completion, embed all KG node descriptions → store in `EmbeddingStore`
4. Replace `KnowledgeGraphManager.retrieve_context()` with hybrid BM25 + KNN via RRF

#### 4.7 RAPTOR-Inspired Hierarchical Summaries

During `VaultCompiler._process_nodes_first_pass()`, after all nodes are built:
1. Cluster character/location/scene nodes by thematic proximity (using embeddings from 4.6)
2. LLM summarises each cluster → Level 1 summary nodes in KG (`type: "summary"`, `level: 1`)
3. LLM summarises Level 1 summaries → Level 2 nodes (`type: "summary"`, `level: 2`)

`PromptBuilder` selects summary level based on context scope: Director gets Level 2, Character Agent gets Level 0.

#### 4.8 Agentic Director (ReAct Tool Calls)

Add a pre-narration "research" phase to the Director's loop in `GameLoopController`. The Director receives a tool manifest:
- `search_knowledge_graph(query)`
- `get_character_profile(name)`
- `get_location_detail(name)`
- `get_relationship(entity_a, entity_b)`

The Director runs a JSON-mode ReAct loop (max 4–5 tool calls) before generating its narrative beat. `LLMClient.gd`'s existing JSON mode supports this without changes.

### RAG001 : Replace VaultCompiler Section Parsing with LLM Extraction (backlog)

**User story:**
* **As a** player importing any Obsidian vault
* **I'd Like to** have all character information extracted accurately regardless of how the vault author structured their notes
* **So that** NPCs have rich, accurate biographies, personalities, and appearances from the first session

**Context:**
- The current `_extract_character_sections()` function attempts to match section headings (`## History`, `## Personality`) using a normalised alias list. It fails on any heading using Markdown bold markers (`**1. History**`) or numeric prefixes, which is the dominant format in most vaults. Nearly every character file produces unrecognised section warnings, and the content of those sections is silently dropped.
- The solution is to replace brittle regex-based extraction with a single JSON-mode LLM call to the Director model per character file. The LLM reads the raw markdown body and extracts structured fields regardless of heading format.
- See Sections 2 (Bug 1), 4.1 of this document.
- Affected files: `src/core/VaultCompiler.gd`

**Description:**
- Remove `_extract_character_sections()`, `_normalize_section_name()`, and `_init_section_aliases()` entirely
- Add `_extract_character_data_via_llm(body, char_name)` that POSTs a JSON extraction prompt to the Director model
- Extract: `biography`, `personality`, `appearance`, `gender`, `goals`
- Fall back to frontmatter keys (`gender`, `pronouns`, `sex`) for the gender field if LLM returns empty
- Write all five fields to node `props`
- Remove all `[VaultCompiler] Warning: Unrecognized section` log lines
- Update `_compiled_data["characters"]` compat dict to include `personality`, `gender`, `goals`
- The Director model (`LLMClient.dm_model`) must be used for this extraction

**Requirements:**
- LLM extraction runs asynchronously during compilation (same thread as existing LLM warmup calls)
- Per-character extraction progress is shown in the existing compilation status UI (SYS025)
- A character with no parsable content must still produce empty-string fields rather than erroring
- The `writing_style` extraction path (separate from section parsing) must remain unchanged
- Compilation must complete cleanly; no partial-state errors if a single character extraction fails (skip and continue)

**Acceptance criteria:**
* **Given** a vault where King Yuna's file uses `**Personality**`, `**1. History**`, `**3. Appearance**` headings
* **When** VaultCompiler runs
* **Then** `props["personality"]`, `props["biography"]`, `props["appearance"]` are all non-empty strings containing the relevant content
* **And** zero `[VaultCompiler] Warning: Unrecognized section` log lines appear
* **And** the compatibility dict entry for `king_yuna` includes `personality`, `gender`, and `goals` keys

### RAG005 : Lower Director Threshold and Inject Narrative Beat (backlog)

**User story:**
* **As a** player
* **I'd Like to** have the story move forward dynamically even if I'm not explicitly pushing it
* **So that** the adventure feels alive and progresses on its own momentum

**Context:**
- The Director fires only after `turns_since_last_director >= 6` AND a non-`"none"` escalation signal from the 3B NPC model (which almost never produces one). This means the story stagnates for 6+ turns. When the Director does fire, its narrative beat is not injected into the subsequent NPC prompt — so the NPC still doesn't know what the Director planned.
- See Section 2 (Bug 7), 4.4 of this document.
- Affected files: `src/core/GameLoopController.gd`, `src/core/PromptBuilder.gd`, `src/autoload/CampaignState.gd`

**Description:**
- Change `turns_since_last_director >= 6` → `turns_since_last_director >= 2` in `GameLoopController._trigger_background_director()`

- The `last_director_beat` injection must not exceed 500 characters in the prompt (truncate with ellipsis if longer)

**Acceptance criteria:**
* **Given** the player has sent 2 messages to an NPC without triggering an escalation signal
* **When** the third player turn begins

### RAG007 : Semantic Embedding Retrieval for KnowledgeGraphManager (backlog)

**User story:**
* **As a** player exploring the world
* **I'd Like to** have the Director and NPC agents find relevant lore by meaning, not just by exact name
* **So that** the story is informed by vault content even when the player's words don't exactly match entity names

**Context:**
- `KnowledgeGraphManager.retrieve_context()` uses substring matching on node labels and IDs. This fails for synonyms, descriptions, and paraphrases ("the blacksmith's son" will not find "Aldric"). Semantic embeddings via Ollama's `nomic-embed-text` model combined with a local `sqlite-vec` vector store enable meaning-based retrieval.
- See Sections 3.4, 4.6 of this document.
- New files: `src/autoload/EmbeddingStore.gd`
- Affected files: `src/core/KnowledgeGraphManager.gd`, `src/autoload/LLMClient.gd`

**Description:**
- Add `LLMClient.get_embedding(text: String) -> Array[float]` — POST to `http://localhost:11434/api/embeddings` with `model: "nomic-embed-text"`
- Create `EmbeddingStore.gd` autoload using `sqlite-vec` GDExtension to store and query 768-dim float32 vectors
- At `VaultCompiler` completion, embed all KG node descriptions and store in `EmbeddingStore` (keyed by node ID)
- Update `KnowledgeGraphManager.retrieve_context()` to run both the existing BM25-style substring match AND a KNN semantic query (top-10), then merge results via RRF (k=60)
- `nomic-embed-text` must be pulled via Ollama before first use; add a check in `LLMClient._test_connection()` or onboarding

**Requirements:**
- Embedding generation at compile time must not block the main thread
- Vector store file stored in user data dir alongside save files
- If `nomic-embed-text` is not available, fall back gracefully to existing substring-only retrieval with a warning

**Acceptance criteria:**
* **Given** the knowledge graph contains a node `"Aldric"` with description `"Aldric is the blacksmith's apprentice"`
* **When** `retrieve_context("the young man in the forge")` is called
* **Then** the `"Aldric"` node appears in the returned context (semantic match)
* **And** the returned context fits within the lore token budget
* **And** the test suite shows no regressions in existing retrieval behaviour

### RAG008 : RAPTOR-Inspired Hierarchical Summary Nodes (backlog)

**User story:**
* **As a** player starting an adventure in a specific region
* **I'd Like to** have the Director understand the big-picture narrative arc of that region
* **So that** the story has coherent themes and the Director can plan meaningful events

**Context:**
- The Director currently receives a flat list of lore nodes from `retrieve_context()`. It has no sense of campaign-level themes, regional arcs, or narrative structure. RAPTOR-inspired hierarchical summaries would give the Director pre-computed thematic context at multiple abstraction levels.

- Affected files: `src/core/VaultCompiler.gd`, `src/core/KnowledgeGraphManager.gd`, `src/core/PromptBuilder.gd`

### RAG009 : Agentic Director — ReAct Tool Calls Before Narrative Generation (backlog)

**User story:**
* **As a** player exploring the world
* **I'd Like to** have the Director look up relevant lore before deciding what happens next
* **So that** the story is grounded in vault details even for situations the Director hasn't encountered before

**Context:**
- The Director currently receives a pre-assembled context and generates a narrative beat in one pass. It cannot look things up. The ReAct pattern lets the Director run a brief research loop before generating — querying the knowledge graph with specific questions until it has enough context. This is the full realisation of the "left brain" architecture.
- See Sections 3.3, 4.8 of this document.
- Prerequisite: RAG007 (semantic retrieval) and RAG008 (summary nodes) for best results
- Affected files: `src/core/GameLoopController.gd`, `src/autoload/LLMClient.gd`

**Description:**
- Before the Director generates its narrative beat, run a JSON-mode pre-narration research phase
- The Director receives a tool manifest:
  - `search_knowledge_graph(query: String)`
  - `get_character_profile(character_name: String)`
  - `get_location_detail(location_name: String)`
  - `get_relationship(entity_a: String, entity_b: String)`
- The Director outputs `{ "thought": "...", "action": "...", "args": {...} }` or `{ "final": true }` to end the loop
- Max 5 tool call iterations per Director activation
- Tool responses are appended to the Director's context for the next iteration
- After the loop, the Director generates the narrative beat with full assembled context

**Requirements:**
- ReAct loop must have a hard timeout (max 60 seconds total)
- If loop times out, proceed to narrative generation with whatever context was assembled
- Director model (`gemma4:e4b`) must be used; Actor model is not used in the loop

**Acceptance criteria:**
* **Given** the player says "I leave the swamp and head north"
* **When** the Director's pre-narration research loop runs
* **Then** the Director calls `search_knowledge_graph("swamp exit north")` at least once
* **And** the resulting context contains information about what lies north of the swamp
* **And** the Director's narrative beat references specific lore from the vault (not invented detail)
* **And** the entire research loop completes within 60 seconds
* **And** the Character Agent's subsequent dialogue reflects the Director's informed narrative beat
